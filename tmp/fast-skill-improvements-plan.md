## Verified facts the plan rests on

- `npm create @wix/new init` in any folder creates a new blank site, its OAuth app (allowed domains: the hosting domain and `localhost:4321`), the hosting project, and writes `wix.config.json` (`projectType: Site`, `appId`, `siteId`, `site.outputDirectory: ./dist`). It refuses when a config exists, generates no files, does not check for Astro.
- `wix build` runs `astro build`. Astro only.
- `wix release` reads `site.outputDirectory` and uploads that directory as a static site. No adapter metadata needed. Any framework's static build can be Wix-hosted; SSR output cannot.
- `deploy.mjs --stack react` exists: copies the vertical's `app/` only and writes the public client id into `src/wix/config.ts`.
- `src/wix/` (data layer, `sdk.ts`, `media.ts`, `cart-store.ts`) imports no React.
- `fast-path.mjs` always runs `wix create` (Astro template) and always requires and runs a `plan.json` seed.
- Every frontend read in fast AND in wix-headless's recipes goes through `@wix/sdk`. Seeds in both are REST. The only REST frontend reference in the repo is wix-vibe-headless's `rest/` layer.
- Today's runs: shipped code gets used; prose rules get skipped.
- `deploy.mjs` patches only the dependencies the copied code imports; `typescript`, `react`, `astro` are scaffold-owned and never added (comment at line 50). It does not require a `tsconfig`. Vite, Next, Astro, and the TanStack templates compile `.ts`/`.tsx` with no configuration (esbuild strips types), so the shipped files build inside a plain-JS project untouched.
- Fast's shipped components are routing-free (plain `<a>`, optional `LinkComponent`); no shipped file imports a router. The vibe failures in #1412/#1413 (18 files importing `react-router-dom`, playbook prose describing one template) cannot recur in fast. Vibe could detect its two Base44 templates; the wild has no finite list, so fast must stay generic: no router detection, no per-template skeletons.

## Stage 1b — Where am I: the folder decides the starting point

**Coverage, 2026-09-26 evening.** The mechanical guard is in (G5 DONE: fast-path and attach refuse on a `wix.config.json` in the CWD). The step 0 prose and its branch are not written; G1 to G4 not run. The entry's Phase 0 says only "work from the folder that will hold the project". Since #1480 every fast project carries an AGENTS.md naming the skill, the site and the skills folder, so the "built here" tell is `wix.config.json` plus `.agents/skills/<this skill>` plus that AGENTS.md, not a composed marker comment.

**The gap.** The entry names three starting points (new, connect, iterate) and tells the agent to read them off the filesystem: empty folder, a project without `wix.config.json`, `.wix`/`wix.config.json` present. Nothing verifies that reading. The failure it invites: the same "build me a store using the skill" prompt pasted into a fresh conversation, in the folder where the last run already built that store. The agent has none of the previous conversation, the prompt says "build", and today's step 3 says "create runs in an empty directory: run the fast path" — so it can scaffold a second site next to the first, or seed the existing catalog twice. The fix is mostly prose: tell the agent to look at the folder before acting and how to branch on what it finds. `wix.config.json` is the one fact worth a mechanical check, so `fast-path.mjs` refuses to scaffold on top of one.

**Adds**
- Entry Phase 2 / SKILL.md step 0 **(new, before "Resolve the stack")**, short prose: *Look at the folder you are in before you act. Is it empty? Does it hold a project, and which stack? ### 4b — Reference mode: a REST layer shipped as code (TypeScript, stripped to JS on deploy)

**Decision.** Not a `REST.md` table: code gets used, tables get skimmed (today's runs). Each vertical ships `references/<vertical>/rest/`, a framework-free twin of `app/wix/<vertical>/` over `fetch`, **written in TypeScript against the same `types.ts`** so parity with the SDK layer is compiler-checked, and **stripped to dependency-free JS at deploy time** for a static site. Ports (Python/PHP/Go) read the `.ts`: types are the field contract a port needs, better than JSDoc. Compared with vibe-headless, which is REST already: vibe splits endpoint knowledge (REST files, 578 lines, no React) from the data rules (React hooks that map raw entities), so a port reconstructs the rules from React code; fast's `rest/` keeps calls, rules, and DTO mapping in one framework-free file. Vibe's header-comment style (about half of each REST file) is the part to copy.

**Scope.** The four transport files alone are not enough for a full store: of the storefront's 2,424 shipped lines, 858 are Wix I/O and 1,566 are the listing state machine, PDP selection logic, cart store, and the three components (filter panel, quick add, drawer) — the logic that exists to stop agents getting variants and overlays wrong. The REST layer therefore has three tiers:
1. transport (`client`, `media`, `catalog`, `cart`) — drafted in `tmp/rest-example/`, smoke-tested live against the run-54 store end to end (reads, facets, detail, variant resolution, add/update/checkout/remove);
2. state without React: `shop-state.ts` (from `useShop`: selection, cursor chain, stale-response guard, URL sync, subscribe/get/set), `product-detail-state.ts` (from `useProductDetail`: selections, `resolveVariant`, `blockedReason`, `canAdd`, quantity reset, `add`), `cart-store.ts` as-is (already React-free);
3. vanilla renderers for the static case only: `filter-panel`, `quick-add`, `cart-drawer` taking the state objects and rendering into a container — the overlay contract and the three purchase paths as code.
